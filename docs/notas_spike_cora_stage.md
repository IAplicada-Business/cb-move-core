# Notas internas — Spike técnico Cora Stage (automação NF pós-pagamento)

**Não enviar ao cliente.** Achados técnicos do spike executado em `scripts/spike_cora_stage.py` contra o ambiente Stage já configurado em `integracao_config` (mesmas credenciais de `emit-boleto-cora`). Confirma/ajusta premissas do plano de arquitetura antes da implementação dos passos seguintes.

## Execução

```
python scripts/spike_cora_stage.py
```

Fluxo: token mTLS → cria boleto de teste (R$ 5,00, CPF de teste `111.444.777-35`) → consulta → paga via `/v2/invoices/pay` (endpoint exclusivo de Stage) → consulta de novo → registra endpoint de webhook (placeholder) → remove o endpoint.

## Achados

1. **Token mTLS**: `POST {CORA_API_BASE}/token` funcionou de primeira com as credenciais já salvas (`CORA_CLIENT_ID` + `CORA_CERTIFICATE` + `CORA_PRIVATE_KEY`). Nenhum ajuste necessário em `_shared/cora.ts::getCoraAccessToken`.
2. **Criação de boleto**: `POST /v2/invoices` retorna `status: "OPEN"` (não `"CREATED"`/`"DRAFT"` como alguns exemplos antigos da doc sugerem). O enum de trigger `created` do webhook corresponde a esse `OPEN`.
3. **Consulta**: `GET /v2/invoices/{id}` funciona com o mesmo token/mTLS. Campo `status` existe no nível raiz do JSON (string) — é esse o campo que o núcleo compartilhado (`cora-payment-sync.ts`) deve checar para decidir "pago" (`status === "PAID"`).
4. **Pagamento em Stage** (`POST /v2/invoices/pay`, body `{"id": invoice_id}`, header `Idempotency-Key` obrigatório — confirmado, sem ele a Cora retorna 400): aceito com `200`. A resposta imediata do `/pay` trouxe `status: "OPEN"` no boleto — **diferente do exemplo da doc pública** (que mostra `"status": "IN_PAYMENT"` logo após o `/pay`; não reproduzimos esse valor em nenhum teste). O array `payments[]` já aparece populado nesse momento com uma entrada `status: "IN_PROCESS"`, `finalized_at: null`. Isso não afeta a automação: nosso código só age quando `status === "PAID"` no nível raiz, então tratamos `OPEN`/`IN_PAYMENT`/qualquer outra coisa da mesma forma ("ainda não pago, não faz nada").
   4.1. **Divergência confirmada entre a documentação pública e a API real (v2/invoices)** — revisão feita em 2026-07-16 contra [`/reference/pagar-boleto-em-stage`](https://developers.cora.com.br/reference/pagar-boleto-em-stage). A doc mostra um schema **camelCase** antigo (`amountTotal`, `documentUrl`, `bankSlip`, `createdAt`, `authenticationId`, `notification`, `payments[].state`/`.amount`). A resposta real (tanto do `POST /v2/invoices` quanto do `POST /v2/invoices/pay` e `GET /v2/invoices/{id}`) usa **snake_case** e uma estrutura diferente:
   - Chaves reais no nível raiz: `id, status, code, created_at, occurrence_date, customer, services, payment_terms, payment_options, payments, pix, total_amount, total_paid`. Não existem `amountTotal`, `documentUrl`, `bankSlip`, `authenticationId` nem `notification` no nível raiz.
   - Boleto/PDF fica em `payment_options.bank_slip.{url, barcode, digitable, our_number, registered}` (não em `bankSlip` no nível raiz).
   - Cada item de `payments[]` usa `status` (não `state`), `created_at`/`finalized_at` (não `createdAt`/`finalizedAt`), `total_paid` (não `amount`), e tem um campo `method` (`"BANK_SLIP"`) que a doc nem lista.
   - **Impacto no nosso código: nenhum.** `_shared/cora-payment-sync.ts` só lê `invoice.status`, `invoice.id` e repassa `invoice.payments` cru para o log (sem depender dos nomes internos). `_shared/cora-invoice.ts` (código pré-existente, usado por `emit-boleto-cora`) já lia `payment_options.bank_slip.url/digitable` e `pix.emv` — ou seja, já estava certo contra a API real, não contra a doc desatualizada. Não foi necessário nenhum ajuste.
   - Também não reproduzimos o erro documentado `REC-0007 "Payment attempt of self issued BankSlip"` ao pagar um boleto emitido com o mesmo `client_id` usado para pagar — em Stage isso não bloqueou o teste.
   - **Conclusão prática:** para qualquer trabalho futuro que precise exibir campos do boleto Cora na UI (ex.: valor, código de barras), usar os nomes reais em snake_case confirmados acima — não confiar na doc pública sem validar contra uma resposta real primeiro.
   - **Causa raiz identificada:** não é inconsistência da nossa integração — é a própria documentação pública da Cora que está dessincronizada entre páginas. As páginas específicas do recurso `v2/invoices` — [`Consulta de detalhes do boleto`](https://developers.cora.com.br/reference/consultar-detalhes-de-um-boleto-v2) e [`Emissão de boleto registrado`](https://developers.cora.com.br/reference/emiss%C3%A3o-de-boleto-registrado-v2) — já documentam corretamente o schema **snake_case** (`status`, `created_at`, `total_amount`, `total_paid`, `occurrence_date`, `payment_options`, `payments`), idêntico ao que capturamos na chamada real. A página `Pagar boleto em stage` (que só existe para dar saldo/testar em Stage) ficou com um exemplo **antigo** (schema v1, camelCase) que nunca foi atualizado quando o recurso migrou para `/v2/`. A própria doc de ["Instruções iniciais"](https://developers.cora.com.br/docs/instrucoes-iniciais) confirma que a Cora versiona por path (`/v2/...`), sem header de versão — reforça que o `/pay` (endpoint auxiliar de Stage, não uma API transacional "principal") simplesmente não recebeu o mesmo cuidado de manutenção da documentação. Vale reportar à Cora, mas não é algo a corrigir do nosso lado.
5. **Latência de liquidação em Stage**: no teste, uma nova consulta ~20s depois já mostrou `status: "PAID"` e `payments[0].status: "SUCCESS"`. Ou seja, em Stage a confirmação é praticamente imediata (segundos). Isso **valida com folga** o intervalo de polling planejado (15–30 min) — o polling vai capturar o pagamento quase que instantaneamente após a liquidação real, e o webhook só reduz essa latência residual, não é indispensável para o funcionamento correto.
6. **Registro de webhook** (`POST {CORA_API_BASE}/endpoints`, mesmo domínio mTLS `matls-clients.api.stage.cora.com.br`, **não** o domínio OAuth `api.stage.cora.com.br` usado nos exemplos genéricos da doc): funcionou com body `{"url", "resource": "invoice", "trigger": "paid"}` + header `Idempotency-Key`. Retornou `id` (`end_...`) que pode ser usado depois em `DELETE /endpoints/{id}` — testado e confirmado (`204`).
7. **Assinatura do webhook**: não foi possível observar uma entrega real (o endpoint de teste apontava para um placeholder `https://example.com/...`, sem receptor). Isso não contradiz a conclusão já registrada na arquitetura (corpo vazio / sem assinatura documentada) — mantém a decisão de nunca confiar no webhook como fonte de verdade e sempre reconfirmar via `GET /v2/invoices/{id}` com mTLS antes de qualquer ação (emissão de NF).

## Impacto na implementação

- O endpoint real de webhook (apontando para a function `cora-webhook` já publicada) será registrado no passo `deploy-teste-stage`, reaproveitando o mesmo `POST /endpoints` validado aqui.
